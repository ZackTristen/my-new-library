## 1 Постановка задачи на разработку адаптивного веб-сайта

### 1.1 Функциональные и архитектурные особенности адаптивных веб-сайтов

Разработка современных веб-сайтов — это комплексная задача, ключевым аспектом которой является обеспечение качественного пользовательского опыта на множестве устройств. Чтобы приложение было востребованным, необходимо не только реализовать задуманный функционал, но и спроектировать гибкую архитектуру, способную адаптироваться к различным условиям эксплуатации.

Базовыми функциями для веб-сайта личной библиотеки являются возможности каталогизации: просмотр списка книг, поиск по атрибутам (название, автор), а также управление личной коллекцией. Для персонализации опыта необходима система аутентификации пользователей. Важным элементом является административная панель для управления основным контентом — базой данных книг.

Помимо основных функций, могут быть добавлены и другие возможности, например, система оценок и отзывов, рекомендации или возможность создавать публичные подборки.

Архитектурные особенности адаптивного сайта определяют его гибкость и масштабируемость.
1.  **Разделение ответственности:** Четкое разделение на клиентскую часть (frontend) и серверную (backend) упрощает разработку, тестирование и дальнейшую поддержку. Серверная часть отвечает за бизнес-логику и работу с данными, а клиентская — за их отображение.
2.  **Модульность:** Frontend-архитектура, построенная на принципах адаптивного дизайна (гибкие сетки, гибкие изображения и медиа-запросы), обеспечивает гибкость отображения на разных экранах. Это позволяет изменять или добавлять новые компоненты интерфейса, не нарушая общую структуру.
3.  **Масштабируемость:** Архитектура должна позволять наращивать функционал без потери производительности. На стороне сервера это достигается выбором подходящего фреймворка, а на стороне клиента — оптимизацией ресурсов и использованием эффективных CSS-подходов.

Компоненты архитектуры в данном проекте включают клиентскую часть, реализованную на HTML и CSS с использованием медиа-запросов, и серверную часть на фреймворке Flask, которая взаимодействует с базой данных для хранения информации о пользователях и книгах.

## 2 Проектирование веб-приложения

### 2.1 Выбор средств разработки

Успешная реализация проекта напрямую зависит от обоснованного выбора технологического стека. Необходимо было проанализировать доступные инструменты для веб-разработки, учитывая такие критерии, как скорость разработки, производительность, масштабируемость и соответствие ключевой задаче — созданию адаптивного интерфейса.

Для серверной части (backend) рассматривались популярные Python-фреймворки.
**Django** — это высокоуровневый фреймворк, следующий принципу «всё включено» (batteries-included). Он предоставляет встроенные решения для ORM, админ-панели, аутентификации и многих других задач [8].
**FastAPI** — современный фреймворк, известный своей высокой производительностью и автоматической генерацией документации API на основе стандартных аннотаций типов Python [9].
**Flask** — это микрофреймворк, который предоставляет базовые возможности для создания веб-приложений, оставляя разработчику свободу в выборе библиотек и подходов. «Flask не навязывает определённую структуру проекта или зависимости, что делает его гибким инструментом для небольших и средних проектов» [10].

Сравнительный анализ фреймворков для backend представлен в таблице 2.

Таблица 2 – Сравнительный анализ backend-фреймворков
| Критерий | Flask | Django | FastAPI |
| :--- | :--- | :--- | :--- |
| Подход | Микрофреймворк | "Всё включено" | Микрофреймворк |
| Гибкость | Высокая | Низкая | Высокая |
| Простота изучения | Высокая | Средняя | Средняя |

Для данного проекта был выбран **Flask**, так как его минималистичность и гибкость идеально подходят для учебного проекта, позволяя сосредоточиться на конкретных задачах, таких как реализация бизнес-логики и работа с базой данных, без необходимости осваивать громоздкую структуру большого фреймворка.

Для клиентской части (frontend) ключевым было решение о подходе к реализации адаптивности.
**Frontend-фреймворки (React, Vue, Angular)** предоставляют мощные инструменты для создания сложных одностраничных приложений (SPA). Они используют компонентный подход и виртуальный DOM, что упрощает управление состоянием и повышает интерактивность интерфейса.
**«Чистый» CSS/HTML/JavaScript** — это фундаментальный подход, при котором весь интерфейс и его адаптивность реализуются с помощью стандартных веб-технологий. Основным инструментом адаптивности здесь выступают CSS Media Queries, которые «позволяют применять разные стили в зависимости от характеристик устройства, таких как ширина экрана».

Так как главной целью дипломной работы является именно демонстрация и исследование возможностей CSS Media Queries для создания адаптивного дизайна, от использования frontend-фреймворков было решено отказаться. Такой подход позволяет получить полный контроль над вёрсткой, оптимизировать производительность за счёт отсутствия лишних зависимостей и глубоко изучить механизмы адаптивного поведения веб-страниц.

В качестве системы управления базами данных (СУБД) была выбрана **SQLite**, поскольку это легковесная, встраиваемая, не требующая отдельного сервера СУБД. Для учебного проекта её возможностей более чем достаточно. Взаимодействие с базой данных реализовано с помощью **SQLAlchemy**, библиотеки, предоставляющей инструментарий ORM (Object-Relational Mapping), что позволяет работать с данными в объектно-ориентированном стиле.

Для разработки использовалась среда **Visual Studio Code**, предоставляющая гибкие инструменты для работы с Python и веб-технологиями.

### 2.3 Выбор архитектуры веб-приложения

Выбор правильной архитектуры — залог создания поддерживаемого и масштабируемого приложения. Для веб-приложений часто рассматривают два основных подхода: монолитная архитектура и микросервисная.
**Микросервисная архитектура** предполагает разделение приложения на множество небольших, независимо развёртываемых сервисов. Этот подход хорош для крупных и сложных систем, но избыточен для небольших проектов из-за сложности в настройке и управлении.
**Монолитная архитектура** представляет приложение как единое целое, где все компоненты тесно связаны и развёртываются вместе. Для проекта «Моя библиотека» этот подход является наиболее рациональным, так как он значительно упрощает разработку и развёртывание.

В рамках монолитной архитектуры часто применяется шаблон проектирования **MVC (Model-View-Controller)** или его вариации. Этот шаблон разделяет приложение на три логических компонента, что повышает его структурированность и упрощает поддержку.
-   **Model (Модель)**: Отвечает за данные и бизнес-логику. В данном проекте эту роль выполняют классы SQLAlchemy, описанные в `models.py` (`User`, `Item`, `Reservation`, `ReadHistory`), и сама база данных SQLite.
-   **View (Представление)**: Отвечает за отображение данных и пользовательский интерфейс. Эту роль играют HTML-шаблоны (Jinja2), расположенные в папке `templates`.
-   **Controller (Контроллер)**: Обрабатывает запросы пользователя, взаимодействует с Моделью и передаёт данные в Представление. В Flask эту функцию выполняют обработчики маршрутов, определённые в `app.py` и `auth.py`.

### 3.1 Реализация серверной части на Flask

Серверная часть приложения была реализована на Python с использованием микрофреймворка Flask. Структура была разделена на несколько модулей для соблюдения принципа разделения ответственности, что упрощает поддержку и дальнейшее развитие проекта.

**Модели данных.** Основой для работы с данными послужила библиотека SQLAlchemy, реализующая паттерн ORM (Object-Relational Mapping). Каждая модель представляет собой Python-класс, наследуемый от `db.Model`, и описывает таблицу в базе данных. Особое внимание было уделено связям между моделями: например, связь "один-ко-многим" между пользователем (`User`) и его книгами (`Item`), предложенными для добавления, реализована через `db.relationship`. Параметр `back_populates` обеспечивает двунаправленность этой связи, а `cascade='all, delete-orphan'` в других связях гарантирует целостность данных, автоматически удаляя связанные объекты (например, бронирования) при удалении пользователя. ### 3.3 Интеграция frontend и backend

Связь между серверной логикой на Flask и клиентским представлением осуществляется с помощью шаблонизатора Jinja2 [3], который глубоко интегрирован во Flask.

**Наследование шаблонов.** Чтобы избежать дублирования кода, был создан базовый шаблон `layout.html`. Он определяет общую HTML-структуру: `<html>`, `<head>` с подключением стилей и мета-тегов, и `<body>` со сквозными элементами, такими как шапка (`header`) и подвал (`footer`). Внутри `<body>` определен специальный блок `{% block content %}{% endblock %}`, который дочерние шаблоны (например, `index.html`) наполняют своим уникальным содержимым, используя тег `{% extends 'layout.html' %}`. В `layout.html` также реализована логика отображения flash-сообщений. Ключевая часть структуры базового шаблона представлена на рисунке 14.

**Передача данных в шаблоны.** В функциях-контроллерах на стороне Flask данные, полученные из базы или сформированные в ходе выполнения логики, передаются в шаблон в виде именованных аргументов функции `render_template()`. Например, в обработчике главной страницы в шаблон `index.html` передается не только список книг `books`, но и списки `genres` для заполнения фильтров, а также текущие значения поискового запроса `search_query` для отображения в полях формы.

**Отображение данных в шаблонах.** В HTML-шаблонах для отображения динамических данных используются управляющие конструкции Jinja2. Цикл `{% for book in books %}` итерируется по списку книг и рендерит HTML-разметку для каждой из них. Условные операторы, такие как `{% if book.status == 'Доступна' %}` или `{% if current_user.role == 'admin' %}`, позволяют кастомизировать вывод в зависимости от данных конкретной книги или прав текущего пользователя. Для генерации URL-адресов повсеместно используется функция `url_for('endpoint_name', ...)` — это позволяет избежать жестко заданных путей и делает приложение более гибким к изменениям маршрутизации.
