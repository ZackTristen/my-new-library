1 Постановка задачи на разработку адаптивного веб-сайта

1.1 Функциональные и архитектурные особенности адаптивных сайтов

Разработка современного веб-сайта – задача многослойная. И, что немаловажно, здесь уже недостаточно просто реализовать набор функций: необходимо обеспечить качественный пользовательский опыт на разных устройствах. Иначе говоря, сайт должен «вести себя» одинаково хорошо в любых условиях.
Для веб-сайта личной библиотеки базовыми являются функции каталогизации: просмотр списка книг, поиск по атрибутам (название, автор), управление собственной коллекцией. Без этого – никуда. Дополнительно требуется система аутентификации, чтобы персонализировать пользовательский опыт.
Отдельного внимания заслуживает административная панель. Она позволяет управлять основным контентом – базой данных книг. Это своего рода «закулисье» системы, но без него работа невозможна.
При необходимости функциональность можно расширить: добавить оценки, отзывы, рекомендации или возможность создавать публичные подборки. Всё зависит от задач и масштаба проекта.
Архитектура адаптивного сайта напрямую влияет на его гибкость и способность к развитию, поэтому здесь выделяется несколько ключевых принципов: разделение ответственности, при котором клиентская часть отвечает только за отображение, а серверная за бизнес-логику и работу с данными (простое правило, но оно отлично работает); модульность, достигаемая за счёт гибких сеток, адаптивных изображений и медиа-запросов, что позволяет изменять интерфейс без разрушения общей структуры и даёт свободу как разработчику, так и системе; а также масштабируемость, означающая, что архитектура должна расти вместе с проектом на серверной стороне через выбор подходящего фреймворка, а на клиентской через оптимизацию ресурсов и грамотную работу с CSS. 
В рамках проекта клиентская часть реализована на HTML и CSS с применением медиа-запросов [7]. Серверная – на Flask и взаимодействует с базой данных, где хранятся сведения о пользователях и книгах [1].

1.2 Формирование требований к веб-сайту

Формирование требований – один из тех этапов, где закладывается успех проекта. Ошибся здесь – и дальше будет только сложнее.
«Требования должны быть четко сформулированы и логически обоснованы, чтобы избежать ошибок на последующих стадиях разработки».
Для их классификации использована модель FURPS+ [15]. Она делит требования на категории: функциональность, удобство использования, надежность, производительность и поддерживаемость. Знак «+» добавляет ограничения – например, к дизайну или реализации.
Стоит отметить: требования не высечены в камне. Они могут уточняться по мере развития проекта. Но если продумать их заранее, это избавляет от серьезных переделок в будущем. И это чувствуется.

2 Проектирование веб-приложения

2.1 Выбор средств разработки

Успешная реализация проекта во многом зависит от того, насколько грамотно подобран технологический стек. На этапе проектирования необходимо было проанализировать доступные инструменты веб-разработки, учитывая скорость создания приложения, производительность, масштабируемость и соответствие основной задаче – разработке адаптивного интерфейса.
Для серверной части рассматривались популярные Python-фреймворки.
Django представляет собой высокоурневый фреймворк, построенный по принципу «всё включено» (batteries-included). Он предоставляет встроенные средства для ORM, административной панели, аутентификации и многих других задач.
FastAPI – современный фреймворк, отличающийся высокой производительностью и автоматической генерацией документации API на основе аннотаций типов Python.
Flask – микрофреймворк, предоставляющий базовые возможности для создания веб-приложений и оставляющий разработчику свободу выбора библиотек и архитектурных решений [16]. Примечательно, что Flask не навязывает строгую структуру проекта, благодаря чему хорошо подходит для небольших и средних приложений.

Для проекта был выбран Flask. Его минималистичность и гибкость позволяют сосредоточиться именно на реализации бизнес-логики и взаимодействии с базой данных, не отвлекаясь на изучение сложной инфраструктуры крупного фреймворка [11]. Для учебного проекта это оказалось особенно удобно.
При выборе технологий для клиентской части ключевым вопросом стал подход к реализации адаптивности.
Frontend-фреймворки – React, Vue и Angular – предоставляют мощные инструменты для создания сложных SPA-приложений. Они используют компонентный подход и виртуальный DOM, что упрощает управление интерфейсом и делает приложения более интерактивными.
С другой стороны, использование «чистого» HTML, CSS и JavaScript позволяет реализовать интерфейс исключительно средствами стандартных веб-технологий. Основным инструментом адаптивности в таком случае становятся CSS Media Queries, которые позволяют применять разные стили в зависимости от характеристик устройства, например ширины экрана [4].
Поскольку основной целью дипломной работы является исследование возможностей CSS Media Queries при создании адаптивного интерфейса, от использования frontend-фреймворков было решено отказаться [5]. Такой подход обеспечивает полный контроль над вёрсткой, снижает количество зависимостей и позволяет глубже изучить механизмы адаптивного поведения страниц. Да и сама структура проекта получается заметно легче.
В качестве системы управления базами данных была выбрана SQLite – легковесная встраиваемая СУБД, не требующая отдельного сервера [12]. Для учебного проекта её возможностей более чем достаточно.
Взаимодействие с базой данных реализовано с помощью SQLAlchemy – ORM-библиотеки, позволяющей работать с данными в объектно-ориентированном стиле [18].
Разработка проекта велась в среде Visual Studio Code, предоставляющей удобные инструменты для работы с Python и веб-технологиями.

2.2 Разработка диаграммы вариантов использования

Диаграмма вариантов использования относится к числу наиболее наглядных инструментов анализа требований. Она фиксирует, кто именно взаимодействует с системой и какие задачи решает. Графические элементы, линии связей и граница системы позволяют быстро идентифицировать роли пользователей и соответствующие им прецеденты. Что важно, такой подход помогает не только глубже понять требования, но и проверить – насколько будущее приложение действительно отвечает потребностям аудитории.

2.3 Выбор архитектуры веб-приложения

Выбор правильной архитектуры определяет возможность создания поддерживаемого и масштабируемого приложения. Для веб-проектов традиционно рассматривают два основных подхода: монолитную архитектуру и микросервисную.
Микросервисная архитектура предполагает разделение приложения на множество небольших, независимо развёртываемых сервисов. Этот подход оправдан для крупных и сложных систем. Однако для проектов небольшого объёма он избыточен, главным образом из-за сложности настройки и управления.
Монолитная архитектура, напротив, представляет приложение как единое целое, где все компоненты тесно связаны и развёртываются совместно. Для проекта «Моя библиотека» этот подход является наиболее рациональным, поскольку он значительно упрощает разработку и развёртывание. Что немаловажно при ограниченных ресурсах.
В рамках монолитной архитектуры часто применяется шаблон проектирования MVC (Model-View-Controller) или его вариации. Данный шаблон разделяет приложение на три логических компонента, что повышает структурированность кода и облегчает его сопровождение.
Model (Модель) отвечает за данные и бизнес-логику. В настоящем проекте эту роль выполняют классы SQLAlchemy, описанные в файле models.py (User, Item, Reservation, ReadHistory), а также сама база данных SQLite. View (Представление) отвечает за отображение данных и пользовательский интерфейс. Эту функцию реализуют HTML-шаблоны Jinja2, расположенные в папке templates [3]. Controller (Контроллер) обрабатывает запросы пользователя, взаимодействует с моделью и передаёт данные в представление. Во Flask эту функцию выполняют обработчики маршрутов, определённые в app.py и auth.py.

2.4 Разработка пользовательского интерфейса

При проектировании пользовательского интерфейса веб-сайта «Моя библиотека» основной акцент делался на простоте, удобстве и адаптивности. Для этого были сформированы несколько ключевых принципов:
	интуитивность и минимализм: интерфейс не должен перегружать пользователя лишними элементами. Все элементы управления размещены на привычных местах, а навигация остаётся понятной даже при первом использовании сайта.;
	структурированность и последовательность: информация на страницах логически сгруппирована, а единый стиль оформления создаёт целостное восприятие интерфейса. Например, карточки книг имеют одинаковый внешний вид во всех разделах приложения;
	адаптивность (Responsive First): интерфейс изначально разрабатывался с учётом различных размеров экранов. Вместо фиксированных размеров использовались гибкие сетки Flexbox, относительные единицы измерения и CSS Media Queries, позволяющие перестраивать элементы под разные устройства. 
Проектирование интерфейса выполнялось без создания детализированных графических макетов. Вместо этого использовались простые проволочные каркасы (wireframes), позволяющие определить расположение основных блоков: навигационной панели, каталога книг, фильтров и подвала сайта.

Цветовая палитра была выбрана спокойной, а акцентные цвета используются преимущественно для кнопок и ссылок. Это позволяет сосредоточить внимание пользователя на основном содержимом. И интерфейс не выглядит перегруженным.

3.1 Реализация серверной части на Flask

Серверная часть приложения написана на Python с использованием микрофреймворка Flask [9]. В проекте определены модели, описывающие ключевые сущности базы данных: User, Item, Reservation и ReadHistory. Параметр back_populates делает эту связь двунаправленной, а cascade='all, delete-orphan' в других связях гарантирует целостность данных. Что это значит на практике? Когда удаляется пользователь, все связанные с ним объекты – например, бронирования – уходят следом автоматически. Фрагмент кода с определением моделей User и Item приведён на рисунке 8.

3.3 Интеграция frontend и backend

Связь между серверной логикой на Flask и клиентским представлением осуществляется с помощью шаблонизатора Jinja2, который глубоко интегрирован во Flask. Чтобы избежать дублирования кода, создан базовый шаблон layout.html. Он определяет общую HTML-структуру: html, head с подключением стилей и мета-тегов, а также body со сквозными элементами – шапкой (header) и подвалом (footer). 
Внутри body определён специальный блок {% block content %}{% endblock %}. Дочерние шаблоны (например, index.html) наполняют этот блок своим уникальным содержимым, используя тег {% extends 'layout.html' %}. В layout.html также реализована логика отображения flash-сообщений. Ключевая часть структуры базового шаблона представлена на рисунке 15.

 

Рисунок 15 – Структура базового шаблона

В функциях-контроллерах на стороне Flask данные, полученные из базы или сформированные в ходе выполнения логики, передаются в шаблон в виде именованных аргументов функции render_template(). Например, в обработчике главной страницы в шаблон index.html передаётся не только список книг books, но и список genres для заполнения фильтров, а также текущие значения поискового запроса search_query для отображения в полях формы. 
В HTML-шаблонах для отображения динамических данных используются управляющие конструкции Jinja2. Цикл {% for book in books %} итерируется по списку книг и рендерит HTML-разметку для каждой из них. Условные операторы, например {% if book.status == «Доступна» %} или {% if current_user.role == «admin» %}, позволяют кастомизировать вывод в зависимости от данных конкретной книги или прав текущего пользователя.
Для генерации URL-адресов повсеместно используется функция url_for('endpoint_name', ...) – это позволяет избежать жёстко заданных путей и делает приложение более гибким при изменениях маршрутизации.
